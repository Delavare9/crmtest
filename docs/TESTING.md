# Тестирование

Пять уровней. Нижние проверяют правила в самой базе, верхние — что тот же результат видит человек с браузером или с `curl`.

| Уровень | Что проверяет | Где | Команда | Сколько |
|---|---|---|---|---|
| Права в базе | Каждое правило доступа, переходов и журнала — прямо в PostgreSQL | `supabase/tests/*.test.sql` (pgTAP) | `npm run db:test` | 87 |
| Аудит Supabase | Встроенные проверки безопасности и производительности | — | `npm run db:advisors` | 0 предупреждений |
| Атаки через API | Попытки обойти правила по REST с публичным ключом и настоящим логином | `tests/api/attacks.test.ts` | `npm run test:api` | 23 |
| Логика интерфейса | Какие кнопки показать для каждой роли и статуса, тексты ошибок | `src/lib/actions.test.ts` | `npm test` | 20 |
| Сквозной сценарий | Полный цикл задачи в браузере от имени трёх человек | `tests/e2e/task-lifecycle.spec.ts` | `npm run test:e2e` | 1 сценарий |

Всё сразу (нужен запущенный локальный стек и `npm run seed`):

```bash
npm run check
```

Тесты в CI запускаются на каждый pull request и push в `main` (`.github/workflows/ci.yml`): в раннере поднимается локальный Supabase, облачный проект не затрагивается.

## Как тест базы притворяется пользователем

Каждый файл pgTAP работает в транзакции с откатом и сам создаёт пользователей (`_fixtures.psql`). Переключение на участника — `pg_temp.act_as('executor1')`: роль `authenticated` плюс JWT с id пользователя, ровно как это делает PostgREST после проверки токена. Есть участники `manager`, `manager2`, `executor1`, `executor2`, `noprofile` (вошёл, но без профиля), `anon` (без входа), `service` (служебный ключ) и `owner` (владелец таблиц, как SQL-консоль администратора).

## Права в базе — полный список

**01 Чтение** (17)
- исполнитель видит только свои задачи
- исполнитель не видит задачи другого исполнителя даже при явном фильтре
- исполнитель видит только объект, где у него есть задача
- исполнитель не видит объект, где у него нет задач
- исполнитель видит свой профиль и профили постановщиков, но не других исполнителей
- исполнитель не видит историю чужой задачи
- исполнитель видит историю своей задачи
- правила переходов видны вошедшему пользователю
- постановщик архивирует задачу исполнителя
- исполнитель не видит свою задачу после архивации
- объект без активных задач исполнителя пропадает из его списка
- постановщик видит все задачи, включая архивные
- постановщик видит все профили
- аноним не читает задачи, профили и историю (3 проверки)
- вошедший без профиля не видит ни задач, ни объектов

**02 Запись** (28)
- клиенту на запись выданы ровно нужные колонки: без id, статуса, автора, дат и архива
- на уровне таблиц у клиента только SELECT; у анонима ничего; DELETE и TRUNCATE нет ни у кого
- исполнитель не может создать объект или задачу (2)
- исполнитель не может изменить название своей задачи
- прямое изменение `status`, `author_id`, `id`, `archived_at`, `object_id` отклоняется (5)
- клиент не может передать свой id или статус при создании (2)
- служебный ключ без пользователя не создаёт задачу: автор неизвестен
- при создании база ставит автора из сессии, статус «Новая» и время
- нельзя назначить или переназначить задачу на постановщика (2)
- исполнитель обязателен
- постановщик правит задачу в «Новая»
- постановщик не правит в «В работе», «На проверке», «Принята» (3)
- DELETE задачи и объекта отклоняется (2)
- пользователь не может поменять себе роль или завести себе профиль (2)
- объект с активной задачей не архивируется; без активных — архивируется (2)

**03 Переходы** (20)
- все пять разрешённых переходов проходят у нужной роли (5)
- исполнитель не может сам принять свою работу
- возврат на доработку без комментария и с комментарием из пробелов отклоняется (2)
- перебор всех 50 пар «из → в» для двух ролей: 45 запрещённых, ни одна не прошла, все с кодом «нет прав» (3)
- «Новая → Принята» и «Новая → На проверке» отклоняются (2)
- чужая и несуществующая задача дают одинаковый ответ «задача не найдена» (2)
- переход в архивной задаче отклоняется
- прямой UPDATE статуса от владельца таблиц и служебным ключом отклоняется (2)
- даже допустимый переход не проходит прямым UPDATE без функции
- аноним не может вызвать функцию смены статуса

**04 История** (14)
- создание пишет `created` с «— → Новая» от постановщика
- каждая смена статуса пишет автора, статусы и комментарий; порядок по id = хронология
- время события ставит база
- правка полей пишет `updated` с «было и стало» только по изменённым полям
- пустое обновление в историю не попадает
- архивация пишет `archived`
- вставка, изменение и удаление истории клиентом отклоняются (3)
- UPDATE, DELETE и TRUNCATE истории отклоняются даже от владельца таблиц (3)
- служебный ключ тоже не удаляет историю
- задачу с историей нельзя удалить даже владельцу

**05 UUID v7** (8)
- генератор установлен
- id объектов, задач и истории — версия 7, вариант `10` (2)
- метка времени в id совпадает с часами базы
- задача, созданная позже, имеет больший id
- 5000 id подряд строго возрастают; 10 000 id без повторов (2)
- переданный вручную id заменяется сгенерированным

## Проверка, что тесты ловят ошибки

Тест, который не падает на сломанном коде, ничего не доказывает. Проверка: временно ослабить защиту в живой локальной базе, запустить `npm run db:test`, убедиться в падении, вернуть базу `npm run db:reset`.

| Ослабление | Что упало |
|---|---|
| Политика `tasks_read` = `true` (исполнитель видит всё) | 5 тестов чтения |
| Снят триггер журнала (история удаляется) | 4 теста истории |
| Исполнителю разрешено принимать работу | 3 теста переходов |
| Клиенту выдано право на колонку `status` | Структурный тест прав |

Последняя строка — причина, по которой появился структурный тест: без него ослабление прав не было видно, потому что правило ещё держал триггер.

## Ручной сценарий

1. Войти постановщиком → «ЖК «Северный», корпус 2» → «Новая задача» → название, исполнитель «Иван Смирнов» → «Сохранить».
2. В карточке задачи: кнопок перехода нет, «Изменить» есть.
3. Войти исполнителем 1 в другом браузере → «Мои задачи» → задача есть → «Взять в работу» → «Сдать на проверку» с комментарием.
4. Постановщик: «Вернуть на доработку» → «Подтвердить» неактивна, пока комментарий пуст → ввести → подтвердить. «Изменить» снова доступна.
5. Исполнитель: «Снова в работу» → «Сдать на проверку».
6. Постановщик: «Принять». «Изменить» исчезла. В истории 7 событий с комментариями.
7. Исполнителем 2 открыть ссылку на эту задачу → «Задача не найдена».

## Демонстрация атаки вживую

Войти исполнителем, открыть консоль браузера (F12) и выполнить — каждый запрос получит отказ от базы, хотя интерфейс обойдён полностью:

```js
// Клиент приложения: тот же публичный ключ и токен, что у интерфейса.
const { createClient } = await import("https://esm.sh/@supabase/supabase-js@2.119.0");
const key = Object.keys(localStorage).find((k) => k.endsWith("-auth-token"));
const token = JSON.parse(localStorage.getItem(key)).access_token;
const sb = createClient(location.origin.includes("127.0.0.1") ? "http://127.0.0.1:54321" : "<URL проекта>",
  "<publishable key>", { global: { headers: { Authorization: `Bearer ${token}` } } });

// 1. Все задачи — вернутся только свои.
console.log(await sb.from("tasks").select("title, assignee_id"));
// 2. Принять свою задачу напрямую — 42501.
console.log(await sb.from("tasks").update({ status: "accepted" }).eq("id", "<id своей задачи>"));
// 3. Принять через функцию — «Переход review → accepted запрещён».
console.log(await sb.rpc("change_task_status", { p_task_id: "<id>", p_to: "accepted" }));
// 4. Стереть историю — 42501.
console.log(await sb.from("task_history").delete().eq("task_id", "<id>"));
```

## Запуск против облака

`test:api` и `test:e2e` берут адрес из `.env.local`. Подставить URL, ключи и пароль облачного проекта — и те же тесты проверят облако. pgTAP против облака: `npx supabase test db --remote` (каждый файл откатывается, следов не остаётся).
