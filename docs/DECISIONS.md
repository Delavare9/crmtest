# Принятые решения

Три группы: решения по неоднозначным местам ТЗ, технические решения и параметры, которые выбирает владелец. В конце — что сознательно не сделано.

Любое решение из первой группы меняется одной миграцией, если заказчик видит иначе.

## Решения по ТЗ

| № | Неоднозначность | Принятый вариант | Где в коде | Статус |
|---|---|---|---|---|
| 1 | Исполнитель при создании задачи | Обязателен. Назначить можно только пользователя с ролью «исполнитель» | `tasks_before_insert`, `tasks_before_update` | Принято исполнителем |
| 2 | Что можно править после создания | Постановщик меняет название, описание и исполнителя только в «Новая» и «На доработке». Объект задачи не меняется, «Принята» заморожена | `tasks_before_update`, права на колонки | Принято исполнителем |
| 3 | Удаление | Мягкое: задача и объект уходят в архив с отметкой кто и когда. Физическое удаление через API запрещено | `archive_task`, `archive_object`, нет `DELETE` в правах | Принято исполнителем |
| 4 | Удаление объекта с задачами | Объект архивируется, только когда в нём нет активных задач (все приняты или в архиве) | `archive_object` | Принято исполнителем |
| 5 | Что пишется в историю | Все события задачи: создание («— → Новая»), правка полей (было и стало), смена статуса, архивация. Пишет только база | `tasks_log_insert`, `tasks_log_update` | Принято исполнителем |
| 6 | Роль пользователя | Одна роль, в таблице профилей. Через API не изменить, только администратор | `profiles`, права | Принято исполнителем |
| 7 | Кого видит исполнитель | Себя и постановщиков (их имена в истории). Других исполнителей не видит | политика `profiles_read` | Принято исполнителем |
| 8 | Архивные задачи | Исполнитель не видит, постановщик видит | политика `tasks_read` | Принято исполнителем |
| 9 | Комментарий к переходу | Обязателен только при возврате на доработку. В остальных переходах необязателен и сохраняется | `task_transitions.requires_comment` | Принято исполнителем |
| 10 | Идентификаторы | UUID v7 во всех своих таблицах. Id пользователей — от Supabase Auth (v4) | `uuid_generate_v7` | Принято исполнителем |
| 11 | Автор и время | Автора, даты и id ставит база. Клиент подставить их не может | триггеры `*_before_insert` | Принято исполнителем |
| 12 | Одновременные действия | Смена статуса блокирует строку. Второй запрос видит новый статус и получает отказ | `FOR UPDATE` в функциях | Принято исполнителем |
| 13 | Регистрация | Отключена. Пользователей создаёт скрипт заполнения | `config.toml`, настройки Auth | Принято исполнителем |
| 14 | Чьи задачи принимает постановщик | Любые, не только свои: постановщик «видит всё» | правила по роли, не по автору | Принято исполнителем |

## Технические решения

**Т1. UUID v7 — своя функция с автопереключением.** Проверено: Supabase CLI 3.0.0 не принимает `major_version = 18`, локальный и облачный Supabase работают на PostgreSQL 17.11, где `uuidv7()` и расширения `pg_uuidv7` нет. Миграция смотрит на версию сервера: на 18+ создаёт обёртку над встроенной `uuidv7()`, иначе — функцию на plpgsql. В своей функции 12 бит после миллисекунд заполняются долями миллисекунды (как в PostgreSQL 18), поэтому id растут и внутри одной миллисекунды. Проверено: 10 000 id подряд строго возрастают, повторов нет.

**Т1а. Почему UUID v7 первичным ключом везде.** Выбор исполнителя: v7 сочетает уникальность UUID без общего счётчика с ростом по времени, как у автоинкремента.

| Что даёт | Как используется |
|---|---|
| Постоянный ключ | Задаётся один раз, не меняется: по нему связываются таблицы, история, ссылки в интерфейсе, внешние системы |
| Порядок по времени прямо в ключе | История задачи сортируется по `id`: внутри одной транзакции `created_at` одинаков, порядок id точный |
| Выборка по времени и курсором по первичному индексу | «Всё после id X», постраничная выдача и докачка изменений без отдельного индекса по дате |
| Вставка в конец индекса | Меньше разбиений страниц и раздувания индекса, чем у случайного v4; заметно на миллионах строк и массовых вставках |
| Генерация без общего счётчика | Id можно создать в любом сервисе или на клиенте и потом объединять данные без конфликтов ключей |
| Идемпотентная вставка | Если id создаёт отправитель, повтор после обрыва связи упирается в первичный ключ — дубль не возникает |
| Id не перебрать | 74 случайных бита: в отличие от `/tasks/41 → /tasks/42`, по id не угадать соседние записи и их количество |

На основе этих свойств строятся повторы запросов, синхронизация между сервисами и докачка изменений. Сам по себе id ничего не защищает.

Границы:
- **Сейчас id создаёт база**, клиент подставить его не может (решение 11, тест в `05_uuid_v7`). Идемпотентная вставка с id от клиента — заготовка на рост: включается выдачей права на колонку `id` с проверкой версии и времени в триггере.
- **Гонки разводит блокировка, а не время в id.** Одновременные действия — `FOR UPDATE` в `change_task_status` (решение 12). Часы разных серверов расходятся, поэтому «кто раньше» по метке надёжно только в пределах одного источника.
- **По id видно время создания** с точностью до миллисекунды. Для задач на объектах это не секрет; для чувствительных данных выбирали бы v4.
- **16 байт против 8 у bigint** — индексы немного больше.
- Пользователи остаются на v4: их id выдаёт Supabase Auth.

**Т2. Служебные функции — в схеме `private`.** Схема не открыта в API, поэтому `role_of`, `require_actor` и функции триггеров нельзя вызвать через `/rpc`. Тест атак это проверяет.

**Т3. Функции триггеров — `SECURITY DEFINER`.** Они выполняются от владельца (иначе клиент не прошёл бы в `private` и не смог бы писать журнал), а кто действует, берут из `auth.uid()`. У всех `search_path = ''`, все имена в коде полные — подмена функций через `search_path` невозможна.

**Т4. Двойная проверка смены статуса.** Функция `change_task_status` ставит метку на время транзакции, триггер без этой метки смену статуса не пропускает и ещё раз сверяет переход с `task_transitions`. В итоге статус не меняется прямым `UPDATE` даже от владельца таблиц или служебным ключом.

**Т5. Действие без пользователя запрещено.** Запросы служебным ключом не имеют `auth.uid()`, и триггеры их на изменение задач и объектов не пропускают. Так в журнале всегда известен автор. Служебный ключ нужен только для заведения пользователей и профилей.

**Т6. Структурный тест прав.** Тест сверяет точный список выданных клиенту колонок. Без него ослабление прав на колонку `status` не уронило бы тесты, потому что триггер всё ещё держит правило. Второй замок не должен становиться последним незаметно.

**Т7. Гонка «создать задачу / архивировать объект».** Триггер создания задачи берёт `FOR SHARE` на строку объекта, архивация — `FOR UPDATE`. Одна транзакция ждёт другую: задача не попадёт в архивный объект, а архив не пройдёт при новой активной задаче.

**Т8. Новые ключи Supabase.** Используются publishable/secret ключи вместо устаревших anon/service_role JWT. Во фронтенд попадают только переменные `VITE_*`; служебный ключ называется `SUPABASE_SECRET_KEY` и в сборку попасть не может.

**Т9. Заполнение через настоящие входы.** `seed.ts` создаёт объекты и задачи от имени постановщика и двигает статусы от имени исполнителей. История в демо-данных настоящая, а сам скрипт — ещё одна проверка, что обычный путь работает.

**Т10. Ошибки на русском из базы.** Функции и триггеры отдают готовые для пользователя сообщения с кодами `42501`, `P0002`, `55000`, `23514`. Интерфейс показывает их как есть, а системные английские ошибки заменяет текстом по коду.

**Т11. После действия перечитываются все запросы.** Данных мало, а так экран гарантированно совпадает с базой, включая поля от триггеров. При росте данных заменяется точечной инвалидацией.

**Т12. ESLint не подключён.** `typescript-eslint` 8.72 не поддерживает TypeScript 7 (ограничение `<6.1`). Качество держит строгий `tsc` (`strict`, `noUncheckedIndexedAccess`, `noUnused*`) и форматтер `oxfmt`. Подключить, когда выйдет поддержка.

**Т13. Лишние сервисы выключены.** Realtime, Storage, Edge Functions и локальная аналитика не используются и отключены в `config.toml`.

**Т14. Зависимости — последние стабильные на 05.11.2026.** React 19.3, Vite 8.3, TypeScript 7.0, Mantine 9.7, React Router 8.5, TanStack Query 5.106, supabase-js 2.119, Vitest 5.1, Playwright 1.64, Supabase CLI 3.0. GitHub Actions: checkout v7, setup-node v7, supabase/setup-cli v3.

## Что не сделано

- **Облачный деплой.** Нужны доступы владельца к Supabase и Vercel. Команды и порядок — в [OPERATIONS.md](OPERATIONS.md), тесты атак запускаются против облака без изменений.
- **Восстановление из архива.** Архив односторонний; вернуть можно только SQL от администратора. Добавить функцию `restore_task` — одна миграция.
- **Комментарий без смены статуса.** Сейчас комментарий есть только у перехода. Расширение описано в [ASSESSMENT.md](ASSESSMENT.md).
- **Разделение сборки на части.** Бандл 857 КБ (251 КБ gzip), Vite предупреждает о размере. Для пяти экранов приемлемо; лечится ленивой загрузкой страниц.
